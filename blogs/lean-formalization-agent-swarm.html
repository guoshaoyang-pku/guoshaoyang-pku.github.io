人月神话的逆向解 · 把 Perelman 证明拆给一个 Agent Swarm

Shaoyang Guo · 研究记录 · 个人主页

这篇文章回答一个简单的问题：一个本来要做几年的数学形式化工程，交给一个分层组织的 agent swarm，一周能走到哪里？

9 月上旬，我们把 Perelman 证明的 Lean 形式化拆给了一个 swarm：顶层是人类主控加 Astra 主控，只给方向、不做执行；中间是五个组长，各认领一条研究路线，把方向拆成带验收命令的任务；底层是一个 DeepSeek Flash 舰队，在三台远程主机上写 Lean、跑编译、留现场。一周之后，仓库里有了 1,000 多条通过 kernel 检查的声明、27 张结果卡和一个可恢复的控制面——但还没有一个完整的庞加莱定理。

这篇文章记录的是一个正在运行的工程系统，而不是一篇宣布数学结论已经完成的论文。仓库当前包含已编译的 Lean 基础、条件接口、模型级结果、上游资料适配和独立审计；它还没有给出一个无条件、完整的庞加莱猜想 Lean 证明。 仓库交接状态 · 快照 2026-09-11

01发生了什么

系统不是从自动派工开始的，而是从一次人机讨论开始的。我和主控 Astra 花了最开始的一段对话做同一件事：把“形式化 Perelman 证明”这个模糊目标，拆成数学上有依赖关系、工程上可以并行的若干方向。拆解的产物不是一份任务清单，而是一张逻辑 DAG 和五个研究组。

之后的一周大致是四段：

阶段一 · 拆解

人机交互定边界。列出证明的逻辑 DAG，把项目切成五个研究组，冻结证据规则：什么算 proved，什么只能算 conditional，什么必须标成 model。

阶段二 · 基线

基础链成型。Ricci-flow 基础设施逐层通过 kernel 检查（D1–D10）；pinned build 固定 61 个 Lean 文件；axiom gate 清点违禁公理为零。

阶段三 · 桥接

热核桥通过独立审计。D11 的 61 条声明只依赖 propext、Classical.choice 和 Quot.sound，import closure 的 10 个源文件 SHA-256 全部与审计一致——但它是欧氏模型级的，不是一般流形上的存在性。

阶段四 · 铺开

研究轨道全面展开。14 条 D12 轨道交付结果卡；D13 的上游适配、集成审计和交叉复核进行中。最新快照：ophis-gpu 83 个任务 verified-by-compile，360-1 与 360-2 各 13 个；语义账本上还有 23 个开放 blocker。

三件事值得单独记住：执行力可以很快聚集；产出的严格部分全部经得起审计；但“完成”两个字仍然轮不到我们说。这套系统真正做出来的，是一个把几年的数学工程拆成可执行、可恢复、可复核单元的控制结构——本文剩下的部分就在讲这个结构。

02逆向的三层结构：P0 给方向，P1 做计划，P2 干活

“逆向”是相对于常见的 swarm 想法说的。常见的想法是正着来：把一个大任务均匀切碎，撒给一群同质的 agent，谁闲了谁领。我们反过来：先让少数“会看地图的”把问题变成方向，再把方向变成计划，最后才轮到大量执行。三层各司其职：

P0 · 人类主控 + Astra 主控

给出几个模糊方向，把项目分成几个小组。这是整套系统里唯一强制人机交互的环节：项目的拆解、方向的划分、边界的设定，都发生在 P0。主控不要求人类一次性写出所有定理——人类给出几个模糊方向、优先级和禁止越界的结论，主控负责把它们变成可审计的研究组，并冻结项目级数学 DAG 和证据规则。此后 P0 的工作是观察：各组的 checkpoint、blocker、ETA 和产物。

P1 · 组长（Astra 级）

每个组一个组长。接收方向之后，组长指定具体的 plan，把 plan 拆成带依赖和验收命令的任务，派发给 fleet，并且尽可能加速。组长最重要的权力是重排自己的局部 DAG：证明过程中经常发现原始接口的假设不正确、过强或缺少关键正则性，这时需要改路线，而不是让 worker 继续向错误方向堆代码。

P2 · DeepSeek Flash 舰队

做具体执行。每个 worker 在独立 worktree 里写 Lean 或研究产物，跑 lake build / lake env lean，写 checkpoint、heartbeat 和 result card；失败、传输中断或数学受阻时保留现场并暂停，而不是硬编一个假结果。

三层不是互相隔离的部门。P0 可以调整组的方向；P1 可以根据实际 blocker 重新规划局部路线；P2 的编译结果和失败原因又会反过来改变 P1 和 P0 的决策。这套角色协议已经写成可长期恢复的控制面：每个 leader 有独立 worktree、checkpoint 和 comms/ 目录；leader 在 comms/outbox/ 生成子任务；dispatcher 负责领取、租约、恢复和编译 gate；integrator 是唯一可以把通过门禁的结果合并进 publication 分支的角色。

一个必须说清楚的现实限制：协议允许 P1 使用 Astra 级模型，但已检查的远程主机目前实际配置的是 deepseek-flash。所以“Astra 级组长 + Flash 执行体”是当前架构的目标接口，已运行的队列仍主要由 DeepSeek Flash 驱动——模型名称不会因为主控用了 Astra 就被静默改写。 infra/swarm/leader_tasks.json · model_note

03分组方法：先列出数学的逻辑 DAG

Perelman 这边的分组不按文件夹名字划分，而是先把证明的逻辑依赖列成一张 canonical DAG，再在图上找可以提前推进的叶子：

左侧主链是 M0 到 M8 的顺序依赖；右侧的三条绕行边是跨层依赖（M1→M4、M2→M4、M3→M5）。颜色是当前证据状态，不是完成度百分比。

这张图表达的是数学依赖，不能直接当任务队列用——Lean 里许多依赖还没有成熟的 API，过早冻结目标只会产出一堆 statement-only 文件。真正的调度图还要回答三个问题：哪些依赖已经通过编译 gate？哪些只是条件接口？哪些可以在上游完成之前先做？于是同一张图展开成五个长期研究组：L1 Lean 基线（integrator）、L2 上游适配（scout）、L3 解析关键路径（builder）、L4 几何关键路径（builder）、L5 拓扑与审计（auditor）。

前瞻式开发：假设前面都证明好了

把逻辑上依赖的内容并行化，靠的是“前瞻式开发”：假设上游都证明好了，先推进后面的证明。关键动作不是给后续任务一个假定为真的 theorem，而是把假设写进接口，并让接口的语义等级保持可见：

一般流形热核尚未完成时，解析组仍然可以并行推进三件事：欧氏 Gaussian 可以是 kernel-checked 的模型定理；条件接口显式写出正则性、可积性、domination 等假设；下游 consumer 在接口上先行编译。等一般流形定理后来出现时，接入一个满足接口的 producer 即可。同样，几何组先完成不依赖曲率的 GHSpace 结果，拓扑组先完成识别证书和反例审计。

这样做的工程价值有四条：

  1. 未来任务的输入格式在上游完成之前就稳定下来；
  2. 假设缺失、方向错误和 API 不匹配会被提前发现；
  3. worker 不必等待整条证明链闭合；
  4. 前瞻产物不会因为“编译通过”而被误标为一般数学结果。

当前 dispatcher 已支持 deps 和 after_terminal 两类依赖——前者要求前置任务通过验证，后者允许消费已结束但可能 blocked、paused 或 needs-review 的结果。

04宇宙监督猜想：每个场论一个组

同一套 P0–P1–P2 结构不只适用于一个数学命题。宇宙监督猜想这边的分组方法换了刀法：目前所有的场论，各分出来一个小组，而不是强迫它们共享一条过早冻结的证明路线：

  • QFT / 规范场论组；
  • 引力 / 时空组；
  • 宇宙学 / 微扰组；
  • 弦论 / 高维结构组；
  • 数值模拟组；
  • 独立审计组（红队）。

每个场论组拥有自己的局部 DAG、模型、文献账本、数值试验和 Lean 接口；只有跨组真正需要的定义和定理才进入全局 DAG，外加一份共享的猜想账本、基准问题和证据规则。这样可以把“不同理论是否支持同一监督机制”变成可测量的工程问题：哪个方向产出了可复现的不变量，哪个方向只产出 statement-only 的猜想，哪个方向需要升级到更强的组长。

05进度 DAG：超节点、ETA 与产物

一个只画节点和箭头的 DAG 是不够的。我们的进度图以研究组为超节点；每个超节点、以及组内 DAG 里的每个具体节点，都必须带两类标记：ETA（完成所需时间的当前估计）和产物数量（已交付的可审计输出），外加状态点。读者由此可以同时回答两个问题：证明逻辑上，哪一项依赖阻塞了后续？工程上，哪个组正在产出可消费的产物、哪个组在等上游？

实线为组间依赖，组内小箭头为任务依赖；ETA 是当前计划的估计，随 blocker 与重规划滚动更新。小屏可左右滑动查看全图。带状态筛选和证据等级的交互版本：Perelman 形式化 Swarm · 进度 DAG（交互版）。

这张图现在是手工维护的静态快照。下一步是由 queue、checkpoint、result card、compile gate 和语义账本自动生成 swarm-state.json，页面只负责渲染：一个任务只有在真实 artifact、编译记录和审计结果变化之后，才会改变节点状态。组长可以继续调整局部方向，主控可以继续重排全局优先级，而人类看到的始终是同一份可追溯的 DAG。

06Lean 真的完成了吗

没有。更准确的说法是：Lean 工程的若干基础层已经真实完成，整个数学目标还没有完成。我们使用五个证据等级，每个节点的产物都必须落在其中一级：

等级含义能否当作完整证明
provedLean kernel 检查通过，依赖和语义范围经过审计仅对该声明及其明确范围
conditional结论已编译，但依赖显式数学假设或 producer不能
model在欧氏、离散或其他具体模型中成立不能外推到一般流形
statement-only只有目标接口或 frontier，没有证明主体不能
upstream source claim上游资料中的声明，尚未在当前 pin 下复现不能

截至快照，已完成的是：可恢复的控制协议、五个研究组的任务 DAG、queue / dispatcher / worker / checkpoint / result card / 编译 gate 全链路、一批 kernel-checked 的中间 Lean 模块、条件接口、模型定理、上游适配计划和负控制。还开着的是：一般流形上的 PDE、热核、DeTurck 短时存在、体积与 IBP、紧性、canonical neighborhood、surgery 和拓扑识别——完整形式化还要求整个依赖锥的 clean rebuild、下游消费、axiom audit 和独立复现。

监督文件对时间的估计是诚实的：有用的检查点需要 12–24 小时的有效执行；一个有界工作周期的复盘是 3–7 天；完整无条件形式化没有可辩护的日历 ETA——“月到年”仍是宽的规划范围，不是测量出来的界限。

能不能发布？可以，但发布对象必须命名准确。现在可以发布的标题是 Poincaré Formalization Swarm: Infrastructure and Verified Intermediate Results；不能发布的标题是 A Complete Lean Formalization of Perelman’s Proof——后者要求整个一般流形依赖链闭合，并由独立 verifier 在 clean worktree 中重现。
