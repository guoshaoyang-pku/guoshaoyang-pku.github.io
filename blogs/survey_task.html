02 MLS-Bench：让 agent 发明可泛化、可扩展的 ML 方法

一句话定义：MLS-Bench（ML Science Bench） 评估 AI 系统能否 发明 可泛化且可扩展的机器学习方法，而不是只会应用已有方法或调参。

为什么需要它

  • 现有 agent benchmark（MLE-bench、Kaggle 比赛）奖励的是 工程能力：改进一个固定实例（数据处理、调参、调试、模型选择）。
  • ML 科学 要求 方法级 idea：新架构、目标函数、组件或优化器，且要在产生它的 setting 之外验证有效。
  • 核心问题：agent 能否创造方法，而不只是提升某个 leaderboard？

规模与结构

140 个任务，12 个领域：

Language Models · 18 Robotics · 12 Vision & Generation · 11 Reinforcement Learning · 13 ML Systems · 10 AI for Science · 10 Optimization & Theory · 13 Classical & Adaptive · 14 Deep Learning · 11 Time Series · 10 Structured & Causal · 10 Trustworthy · 8

  • MLS-Bench-Lite：30 任务挑战性子集，覆盖全部 12 领域，方便快速迭代。
  • 计算成本：全套 704.7 H100-hours；Lite 仅 99.2 H100-hours（≈4 张 H100 跑 1 天）。

任务结构（每任务 5 要素）

要素说明
(i) 研究问题描述研究问题、背景和目标（可执行形式）
(ii) 代码库 + 可编辑范围限制 agent 能改哪些区域，防止改评估器/训练协议/加容量作弊
(iii) ≥3 个强人类基线含社区认可的 SOTA 方法（可复现）
(iv) ≥3 个评估 setting跨 benchmark、环境或 base-model 规模验证泛化
(v) 种子策略多 seed 运行，保证非偶然

任务接口细节（raw，来自任务页原文）

以下内容直接取自 mls-bench.com 任务页，展示 agent 实际面对的可编辑接口 —— 这是理解"observable 从哪来"的关键。

示例 A：llm-qat-algorithm —— 可编辑文件 custom_qat.py

研究问题：设计一个 QAT 算法，最小化全精度 Pythia-1.4B 与 INT4/INT3/INT2 量化后模型的 perplexity gap。必须是训练侧贡献（fake-quant forward、梯度流、可学习参数、优化器调度），且需在 4/3/2-bit 统一有效。

可编辑范围：只能编辑 # EDITABLE REGION START / END 块内的：

  • CONFIG_OVERRIDES dict：learning_rate / num_steps / batch_size / gradient_accumulation_steps / max_grad_norm / warmup_steps / weight_decay
  • fake_quantize_weight(weight, num_bits, group_size)：可微 fake-quant，梯度须回流到原 weight
  • fake_quantize_activation(x, num_bits)：可选（默认 identity，weight-only）
  • quantize_dequantize_weight(weight, num_bits, group_size)：no-grad 真实 QDQ，训练后物化整数模型用于评估
  • class QATWrapper(nn.Module)：包装 nn.Linear，forward 里做 fake quant；可持额外可学习参数（LSQ per-group scales、StableQAT EMA buffers）；可暴露 aux_loss(step, total_steps)
  • prepare_qat_model(model, num_bits, group_size)：把每个 nn.Linear（及 HF GPT-2 Conv1D）替换为 QATWrapper；必须把 LM head 恢复为 plain Linear（全精度）

固定（不可编辑）部分：模型加载（Pythia-1.4B FP32 + 梯度检查点）、WikiText-2 数据采样（block-1024 随机裁剪）、QAT 训练循环（AdamW、cosine LR + warmup、grad-accum、grad-norm clip）、训练后 real-quantization roundtrip、WikiText-2 test perplexity 评估。

评估：三个 bit-width —— qat-1b-int4（易）/ qat-1b-int3（中，8 级）/ qat-1b-int2（极难，4 级）。主指标 wikitext2_ppl（越低越好），次指标 degradation = ppl - fp16_ppl。

关键对照基线：finetune_then_ptq（先全精度 finetune 再 RTN 量化）—— 隔离 finetune 信号与 QAT 信号。一个有效的 QAT 方法必须击败它，否则其收益只是 in-domain finetune 的功劳。

示例 B：ai4sci-inverse-diffusion-algo —— 可编辑文件 algo/custom.py

研究问题：用预训练扩散先验 p(x) 解逆问题。给定前向算子 A 和观测 y = A(x) + noise，从后验 p(x|y) ∝ p(y|x)p(x) 采样重建 x。

可编辑范围：整个 algo/custom.py，需实现 Custom 类：

  • __init__：scheduler、optimizer、超参
  • inference(observation, num_samples)：给定观测 y，返回重建 x

可用组件（固定）：

  • self.net(x, sigma) → denoised estimate（Tweedie's formula: E[x₀|x_t]）
  • self.forward_op.forward(x) → A(x)
  • self.forward_op.gradient(x, y, return_loss=True) → (∇ₓ‖A(x)−y‖², loss)
  • self.forward_op.loss(x, y) → ‖A(x)−y‖²
  • Scheduler(num_steps, schedule, timestep, scaling) → 扩散噪声调度
  • DiffusionSampler(scheduler).sample(model, x_start) → 无条件采样

评估：三个科学逆问题 —— Inverse Scattering（光学断层，PSNR/SSIM）、Black Hole Imaging（EHT 稀疏干涉观测重建黑洞图像，PSNR/blur-PSNR/closure-phase χ²）、FFHQ256 Inpainting（box mask + σ=0.05 高斯噪声，PSNR/SSIM/LPIPS）。

任务 5 要素（结构复述）

  • (i) 研究问题 → (ii) 代码库 + 可编辑范围 → (iii) ≥3 强人类基线 → (iv) ≥3 评估 setting → (v) 种子策略（多 seed 保证非偶然）
  • 这条链的核心：可编辑范围 定义了 agent 的"干预空间"，多 setting + 多 seed 定义了"泛化验证" —— 这正是闭环里"干预"和"防自欺"的结构化体现。

Agent 预算设计（当前官方值）

官方默认预算（configs/react.yaml + 论文 4.1）：

  • max_steps = 20（action 上限，整个任务）；Lite 扩展模型 8 actions
  • max_tests = 3（test 调用上限）；Lite 扩展模型 1 test
  • 5 小时探索预算/任务（timeout_sec=18000，Harbor 渲染路径）
  • thinking budget = 10,000 tokens/次调用（Anthropic extended thinking 的每请求参数，非全程累计）
  • web search 默认关闭

关键理解：

  • 10k thinking tokens 是「每次 LLM 调用」的限制，不是整个任务 —— 20 个 action 全程可用 ~200k thinking tokens。
  • 1 个 action ≈ 1 次 LLM 调用 + 1 个工具操作（edit/test/submit/undo）。
  • 官方 20 actions / 3 tests 是刻意的公平基准，非技术上限 —— 论文 Test-Time Scaling（5.1）证明：更多 compute/action 在简单任务上收益很快饱和，复杂任务上突破不了 Human SOTA。
  • Verifier-Limited 实验（5.2）把预算放宽到 50 actions / 20 tests，性能反而普遍下降 —— 更多探索不一定更好。
OPHIS 角度：我们后面会增加预算（增大 max_steps/max_tests）。这不会破坏官方可比性（我们本来就不是复现 leaderboard），而是为了：① 给 agent 足够的科学判断空间；② 对比「固定预算下 observables 增强」vs「单纯加预算」哪个更有效（对应 Claim 2/3）。

如何实际运行 MLS-Bench agent（两条路径）

路径 A：Native runner（论文主实验用，自带 ReAct agent）

  • 安装：pip install -e ".[agent]"（Python 3.10+）
  • 配置 configs/react.yaml：填 provider API key（openai/anthropic/deepseek/qwen/gemini/kimi/glm 均可），设 container_runtime: docker|apptainer|local
  • 拉取并构建任务包： 
    mlsbench fetch --name <package>
mlsbench build <package> --config configs/react.yaml
  • 跑 agent（自带非交互 ReAct 循环，不会停下来问用户）： 
    mlsbench agent <task> --model <model> --config configs/react.yaml
mlsbench score task <task>
  • 预算可改：configs/react.yaml 里的 max_steps / max_tests（默认 20/3）
  • agent 类型：InteractiveAgent（ReAct）、OpenEvolveAgent（population 进化搜索）、DiscoverAgent（TTT-Discover）

路径 B：Harbor 数据集（官方 leaderboard 用，兼容任意 agent）

  • 140 任务预渲染成 Harbor 格式，任何 Harbor 支持 agent（claude-code / codex / openhands / terminus-2 / kimi-code 等）都能跑：
  • PYTHONPATH=. harbor run -c run.yaml -a claude-code -m anthropic/claude-opus-4-7
  • 每个任务内置 timeout_sec=18000（5h 探索预算）+ task-specific verifier timeout
  • 官方 leaderboard 全部在 Harbor + 5h 预算下产生 —— 要可比性必须走这条路
  • 注意：Claude Code / Codex 这类交互式 agent 默认会在模糊处停下来问用户；要无人值守需加 --dangerously-skip-permissions 等非交互 flag，或改用自带 native agent
OPHIS 运行建议：我们要做 observables 增强 + 自定义预算，建议走 Native runner 并改造 agent（工具可扩展：在 edit/test/submit/undo 之外加观测工具）；不用 Harbor（它面向现成交互 agent，且不支持自定义预算的可比性保证）。

当前结果（MLS-Bench-Lite，15 个模型）

  • 即使给 agent 强基线 + 多次迭代机会，前沿 agent 仍远不能稳定匹配人类设计的方法。
  • agent 更擅长 工程式调参，不擅长提出能在受控验证下存活的新方法。
  • 作者关键洞察：瓶颈不在「提出」新方法，而在 科学判断 —— 形成假设、选择有信息量的实验、分配有限试验、把反馈转化为可扩展证据。更多搜索 / compute / context 无法消除此瓶颈。
对 OPHIS 的启示（本文作者的连接，非论文原话）：论文指出的瓶颈 —— "scientific judgment needed to form hypotheses, choose informative experiments, allocate limited trials, and turn feedback into evidence" —— 与 OPHIS 的 observable 闭环目标高度吻合。但论文本身没有提出 observable 框架，它只是诊断了 agent 的缺陷。OPHIS 的定位是：用更好的 observables 回应这个"科学判断"瓶颈。
契合点（OPHIS 解读）
  • 每任务 = 可控闭环（明确干预目标、强基线、跨 setting 验证）
  • 有 AI for Science 领域，与 LIGO 同族
  • 任务原子化，适合观察→诊断→干预→再观察
注意
  • 计算成本高（Lite 也 ~100 H100-hours）
  • 评分归一化到基线，单任务改进幅度可能很小

03 EdgeBench：真实环境中的长期学习（含 LIGO 引力波）

一句话定义：EdgeBench（ByteDance Seed） —— 134 个真实世界任务，衡量 agent 从真实环境中持续学习的能力：不是一次性能力，而是长期交互中的改进轨迹。

核心发现（环境学习 Scaling Law）

  • 分析 ~38,000 小时 agent 环境交互。
  • 整体性能遵循 log-sigmoid 缩放律：S(t) = Smax / (1 + (tmid/t)β)，拟合 R² = 0.998。
  • agent 学习速度约每 3 个月翻倍（跨模型世代）。

特点说明
环境学习导向workspace、反馈信号、评估器贴近真实实践；分数反映「如何学习和改进」
超长时程每任务 ≥12h；部分 >72h；人类专家平均 57.2h/任务，最长 320h
六类能力域科学问题 & ML、系统 & SE、专业知识工作、组合优化、形式化数学、交互式游戏

LIGO 引力波任务（协作文档重点，属于完整 134 集，不在开源 51 内）

  • 任务：从 LIGO 探测器数据中 重建引力波波形（H1 波形）。
  • 反馈：多级反馈（分数、误差信息、改进提示）。
  • 示例运行（GPT-5.5，12 小时）：分数 42.8 → 67.0，共 247 次计分尝试。
  • 改进轨迹：先让任务可度量 → 分解失败 → 识别瓶颈 → 保留有效部分并修正剩余错误。
  • 最后阶段：针对 residual / phase / narrow-band 误差定向修正，H1 波形质量提到 67.0。
注意：协作文档写「EdgeBench: 通过 LIGO 数据重建引力波」。EdgeBench 的引力波任务正是 waveform reconstruction（信号重建，逆问题），与 MLS-Bench 的 diffusion-prior inverse solver 同族。但它属于完整 134 任务集（需联系 ByteDance 获取），不在公开的 51 个开源任务里。用开源子集跑的话，对应的是下方 Scientific & ML 类任务。

EdgeBench 评估 harness：SForge（raw）

EdgeBench 由 SForge 驱动 —— 一个双容器（two-container）长时程评估框架：

  • 双容器隔离：每个任务物化为隔离的 work 和 judge Docker 镜像 —— agent 只能看到 work 环境，隐藏测试在一次性 judge 容器里跑，从根源防止评估作弊。
  • 迭代评估 + 反馈：agent 不是最后提交一次拿一次性分数，而是全程反复提交（sforge-submit），收到细粒度反馈（pass rates、失败测试、分数），持续改进直到超时 —— 所有提交中的最佳结果 = 最终分数。
  • Stop Hook：阻止 agent 过早退出 —— 当 Claude Code/Codex 认为任务完成想退出时，hook 拦截退出请求并返回阻塞信号要求继续工作，确保 agent 用完分配的时间。
  • Auto-Resume：agent 异常退出（API 断连、瞬时错误）时自动用原生 resume 机制重启（claude --continue / codex exec resume --last），最多 100 次重试。
  • 后台 auto-eval daemon：可选的周期性后台评估，agent 不提交也在跑。

04 ARC-AGI-3：第一个交互式推理基准

一句话定义：ARC-AGI-3 衡量 AI agent 在 新颖环境 中探索、即时获取目标、构建可适应世界模型、持续学习的能力。100% 分数 = 像人类一样高效地打赢每个游戏。

与 ARC-AGI-1/2 的区别

ARC-AGI-1/2ARC-AGI-3
格式静态推理（输入输出 grid 对）交互式游戏环境
反馈一次性给定输入输出每步 action 返回 frame + 元数据
漏洞可 test-time compute 暴力采样环境只在行动后揭示规则，无法预生成 10000 候选
分数单次正确率效率加权（动作越少分越高）

游戏机制（技术细节）

  • Turn-based：agent 与 2D grid 环境通过标准化 action 接口交互。
  • Grid：最大 64×64；cell 值 0-15（状态/颜色）；坐标 (0,0) 左上。
  • 7 个标准动作：RESET / ACTION1-4（上下左右）/ ACTION5（交互等）/ ACTION6（带 x,y 坐标）/ ACTION7（Undo）。
  • Game State：NOT_FINISHED / WIN / GAME_OVER（达最大动作数等）。
  • 关键设计：每步收到 1-N 帧 JSON（游戏状态 + 元数据），元数据标明哪些动作当前可用。

具体任务示例：ls20（Agent reasoning）

  • 人类表现：100%（776 次总动作完成游戏），7 个关卡。
  • 环境标识：grid 游戏；agent 通过 7 个标准动作交互；每步返回帧 + 元数据（可用动作）。
  • 模型表现（2026-04 ~ 07 公开发布，arcprize.org/tasks/ls20 原文数据）：

重要洞察：动作数多 ≠ 得分低。模型用接近人类（776）的动作数（594-650）却只得 ~5% 分 —— 说明模型在策略分布上与人类完全不同：可能在前几关大量探索，但没真正理解机制。效率加权评分直接惩罚「无效探索」。

评估方式（效率加权）

  • 得分 = 完成游戏的效率（与人类最优动作数比较）。
  • agent 不知道自己被如何评分，全程看不到分数 —— 只返回文本 frame 和关卡信息。
  • OpenAI 发现两个设置能显著提分：用 Responses API（保留 reasoning）+ 开启 compaction。说明推理保留 + 上下文管理对交互式推理至关重要。

OPHIS 视角（本文作者解读，非 ARC-AGI-3 论文原话）：ARC-AGI-3 论文（技术报告）没有使用 "observable" 或 "闭环" 概念。它描述的是 agent 通过动作与环境交互、每步获得 frame 与元数据。把 "frame + 元数据" 解读为 OPHIS 的 "observable 流" 是本文的映射 —— 因为 agent 确实依赖这些观测来推断世界规则、决定下一步动作（即干预）。
契合点（OPHIS 解读）
  • 每步 frame + 元数据 = 天然 observable 流
  • 效率加权评分 = 直接惩罚无效探索
  • 隐藏目标/规则 = 需要主动诊断环境
注意
  • 动作接口受限（7 个动作），observable 主要是视觉帧
  • 135 环境无指令/无规则/无目标，评分惩罚暴力搜索（人类 10 步 vs AI 100 步 → 得 1% 不是 10%）

05 nanoGPT：作为 OPHIS 的可控 example

为什么是好 example：nanoGPT 是 Karpathy 的最小可训练 GPT 实现 —— 完全可控、丰富 observable、已有大量基础、从零可复现。

独特优势

  • 完全可控：训练脚本、数据、超参简单，可精确复现。

nanoGPT 具体任务设定（本项目的闭环平台）

nanoGPT 是 Karpathy 的最小可训练 GPT 实现（GitHub: karpathy/nanoGPT）。核心是 train.py 训练脚本 + model.py（GPT-2 风格 decoder-only transformer）。本项目用它作为 OPHIS 的 example，具体 task 设定：

  • 训练：自回归语言建模，next-token prediction，cross-entropy loss。
  • 数据：OpenWebText 或 TinyStories 等；本项目用 n-gram 频率可控的合成数据（5-gram）来精确操控 token 频率分布。
  • 架构：decoder-only transformer（n_layer/n_head/n_embd 可调），可加/改组件（采样、词表、记忆机制）。
  • 观测维度（observable）：
    • train/val loss 曲线（按 step 记录）
    • gap = train loss − val loss（本项目核心指标，已建立 (K-1)/r 定律：gap 随词表/频率的标度关系）
    • table RMS：词表表项统计与 loss 的对齐诊断
    • token 频率分布、梯度范数、激活分布、attention 模式
  • 干预空间：改采样分布、改词表、改记忆机制、改训练超参（LR/schedule/batch）、改架构组件。

注意：这里 "observable" 是本项目自己的分析框架 —— nanoGPT 本身不提供所谓 "observables"，它只是一套可观测的训练日志。如何从这些原始日志中选择/组合/设计 observables，正是 OPHIS 要研究的问题。

6.2 Observable 闭环的缺陷在哪里

缺陷 1：诊断 → 干预的归因问题（根本性）

闭环里最脆弱的一环是「诊断出的原因」是否真是「干预成功的因果机制」。

  1. 相关性 ≠ 因果：观察到的 observable（loss 翘起、gap 大）可能是多个机制的共同表现。agent 可能选了一个「看起来对症」的干预，其实碰巧有效/无效。
  2. 缺少反事实：人类科学家用消融实验、控制变量验证因果；但闭环 agent 通常只看到「干预前 vs 干预后」两条曲线，无法区分「这个干预有效」与「任何改变都有效」（seed 运气、隐式超参改变）。

缺陷 2：observable 的「信息效率」问题（Claim 2/3 核心）

  1. 原始 observable 太多：训练日志、曲线、中间状态海量。盲目全给 → 上下文爆炸 → 信息过载 → 性能下降（正是 Claim 2 说的「饱和甚至有害」）。
  2. 可观察 ≠ 可诊断：即使 observable 完整，agent 也可能不知道看哪里。例如关键信号可能是「某频率 bin 的 loss 翘起」，但原始 loss 曲线看不到。
  3. 缺少「实验设计」的 observable：目前 observable 都是「被动观察训练」，缺少「主动实验」观测 —— 比如「如果我干预 A，会发生什么」的反事实观测。这是闭环里最缺的。

缺陷 3：闭环的「探索-利用」权衡

  1. 干预次数有限：每次重跑都花 compute（MLS-Bench ~5-10 H100-hours/任务；EdgeBench 12h）。agent 需在有限预算内决定「深入一个假设」vs「尝试多个假设」。
  2. 缺「下一个实验该做什么」信号：现在的 observable 描述「当前状态」，但闭环最需要「哪个实验最有信息量」——这本身需要元认知。

缺陷 4：闭环的「自欺」风险（过拟合闭环本身）

  1. 对当前任务过拟合：agent 可能学到「这个 observable 对应这个干预」，换任务就失效。这正是 MLS-Bench 设计多 setting 验证的原因。
  2. 对 observables 过拟合：若 agent 发现「loss 曲线形态」与「最终分数」相关，可能直接优化 loss 曲线形态（如刻意降 LR 让曲线平滑），而不解决真正问题 —— 一种 observable 作弊。

缺陷 5：闭环缺少「人类科学家的隐性知识」

  1. 先验知识：人类知道「梯度爆炸通常调 clip」「loss 平台可能是 LR 问题」。LLM 先验覆盖一部分，但不覆盖领域特定知识。
  2. 「直觉」不可编码：很多科学判断（这个实验值得做吗）难以用 observable 形式化。

缺陷 6：评估闭环本身的指标缺失

  1. 没有标准指标衡量「诊断质量」：目前只衡量最终分数（干预好不好），不衡量诊断对不对。
  2. 无法区分「运气好」和「诊断对」：单次闭环成功可能是偶然；需多次重复 + 统计。

07 下一步行动建议

  1. 选 3 个闭环（建议组合）：
    • nanoGPT —— 最可控，已有基础，作为 example + 方法论开发地
    • MLS-Bench-Lite 的 1-2 个任务 —— 如 llm-qat-algorithm 或 ai4sci-inverse-diffusion-algo（AI for Science + 训练闭环）
    • EdgeBench 的 LIGO 引力波任务 —— 真实科学问题，需联系 ByteDance 获取完整任务；或先用公开 51 任务里的 Scientific & ML 任务
    • ARC-AGI-3 可作为补充/探索（交互式、成本低但评价标准不同）
  2. 先做一个「最小 observable 闭环」原型：在 nanoGPT 上实现「观察→诊断→干预→再观察」，把闭环的缺陷暴露出来（特别是归因问题）。
  3. 针对 Claim 2/3 做可控实验：同一任务，给 agent 不同数量的 observable（少量精选 vs 海量原始），测量闭环改进效率 —— 直接验证「盲目加 observable 会饱和」和「OPHIS 能提升信息效率」。
  4. 探索「主动实验」observable：让 agent 不只被动看训练，还能主动设计小实验（如 probe 中间状态），这可能解决缺陷 2.3。
